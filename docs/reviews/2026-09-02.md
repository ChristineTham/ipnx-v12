**Numbers.** 102 decisions recorded, 62 of them today. `type.md` is 690 lines,

claim of coherence is a reading of documents, not of behaviour.

## ⚫ Black — what could go wrong

**Two gaps genuinely block the demo. Neither is outside its boundary.**

**1. The status line has no specification.** Christine's demo requirement names
it explicitly — *"status bar in accordance to spec"* — and the spec says only
that the manager writes it and the surface draws it, plus **one** required
entry: the match count after Find. What a text window reports, what a directory
window reports, what a shell window reports: undesigned. This is the clearest
gap and it sits squarely inside the boundary.

**2. Layout placement is not expressible.** `/type/inode/system/breakpoints`
declares **how many columns** at a given width. It does not say **which window
goes where**. The demo's shape is specific — directory on the *left*, three
editors as *tabs in the main area*, `rc` in a row *below* — and nothing in the
design assigns windows to positions. Today the shape comes from `/rc/emca`'s
open order plus the compositor's alternation, which is an accident of sequence
rather than a stated intent. **A demo whose layout cannot be specified cannot be
rebuilt to spec.**

**Three more that will bite during the build, though each is smaller:**

- **`emcaopen` takes a type argument** (`emcaopen text /etc/motd`) and type is
  now **inferred from content**. Both `/rc/emca` and `/rc/emcaopen` need
  redesign, and neither interface is specified.
- **Creating the shell window.** `manage` on `/` produces a process and `shell`
  converses with it — but how `/rc/emca` expresses *"start rc and open a shell
  window on it"* is unwritten.
- **The manager interface's content half is still open** (`window.md:160`):
  whether the *content* is a file too. `text/plain`'s manager is host-side, so
  the demo needs this answered on its first window, not eventually.

**And the risk that is not a gap: everything built today is the superseded
model.** The compositor is green, but it lives in the kernel, which this design
removes. The demo cannot be "rebuilt to the new design" incrementally on top of
it; the window system has to move first.

## 🟡 Yellow — what genuinely works

**The one-rule tests keep passing.** `/home/<x>` over `/<x>` generated the
configuration story, `su`, and `sudo` with no new machinery. *Bind what stays
shared, copy what becomes yours* explained the package/template asymmetry
without special cases. The package format turned out small **because the system
does not mutate**, and that was measured rather than asserted.

**The compositor is real.** M15a–e is built, tested and green — allocation,
alternation, sizing, geometry, the root convention. Its *location* is wrong, not
its behaviour, so the work transfers.

**And the demo's hard parts are the ones already done.** Tabs, allocation and
resize — the things that usually sink a window system — are the built half.

## 🟢 Green — alternatives

- **Build the demo against a deliberately reduced spec:** status line shows
  nothing but the match count; layout hardcoded in `/rc/emca` as it is today.
  Fast, and it would test the type system and the manager interface, which are
  the genuinely new parts. Cost: it would not be "to spec", which is the thing
  she asked for.
- **Design the two gaps first** — a status-line vocabulary and a layout
  declaration — then build. Both are small: the status line is a list of what
  each manager reports; the layout is one more file in `/type/inode/system/`.
- **Move the window system out of the kernel first**, then rebuild the demo on
  it. The largest single piece of work, and everything else waits on it.

## Design thinking — who this is for

**The demo serves P1 and P2, and they want different things from it.**

**P1 — the author-operator.** The demo *is* her daily-driver gate: her belief
test is *"this repository's documents are written and edited from inside the
system"*. That demands the `edit` role on `text/plain` working properly —
Save, Revert, Undo, Find-as-multi-cursor — far more than it demands
architectural purity. **The risk this lens surfaces: today's design optimised
for coherence, and P1 needs it to be usable.** A beautifully layered system in
which she cannot comfortably edit a file fails her test completely.

**P2 — the diaspora.** Their belief test is *"the software behaves the way they
remember"*. The demo shows `rc` — so the `shell` role, line discipline and the
transcript-as-file matter to them specifically, and a terminal that drops
keystrokes when output arrives would fail them on first contact.

**Nothing in today's design was driven by either.** It was driven by internal
consistency — which produced good structure, and is not the same as producing
what someone needs. The status-line gap is the concrete instance: it went
unnoticed for a day because no one asked *what does a person need to see*.

## Virtue ethics — the character of the work

**Truthfulness** — recovered, uncomfortably. The morning began with invented
types in the specs, an invented constraint quoted back at her as evidence, and
`Add` sitting unendorsed. Each was found by *her*, not by me. It ends with every
live spec current and superseded entries marked. The virtue is being practised;
it was not practised well enough to catch these unaided.

**Temperance** — the day's live vice. Sixty-two decisions in one session is not
restraint of scope, and the discipline that held was hers: *"stop, don't
overdo"*, *"we haven't finished designing yet"*, *"accept your proposals"* as a
deliberate stopping point.

**Phronesis** — the blue hat named **analysis paralysis** as this phase's live
risk on 2026-08-29, and today is what that risk looks like: a hundred decisions,
no code. The disposition then was *"the next commit builds"*. It still is.

**Courage** — the specific act now required is *declaring the design done
enough*. Four small gaps stand between here and a buildable demo. The temptation
is to keep designing, because designing has gone well today and building will
expose what document-reading cannot.
